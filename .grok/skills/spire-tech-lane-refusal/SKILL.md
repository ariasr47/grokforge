# Lane refusal — stay in your dir

Own **build-lane boundary refusal craft**: recognize sibling-lane and contract-edit requests, refuse
with a clear bounce, and never "just this once." Roles still own write_scope; this skill is the
refusal method.

**Exit artifact:** refusal text in the role report / GATE Z note — not a parallel REFUSAL.md.

## Critical procedure

1. **Name the forbidden ask.** Sibling lane (backend↔frontend), contract edit (SPEC/INTERFACE/PLAN),
   or path outside write_scope.
2. **Refuse explicitly.** Do not partially implement the forbidden work.
3. **Route, do not absorb.** Point to GATE Z amendment, the owning lane, or missing INTERFACE fields.
4. **Preserve evidence.** Quote the request or path that crossed the boundary.
5. **Continue only in-lane work** if the original dispatch still has allowed scope.

## Stop conditions

Stop when write_scope is ambiguous in the contract and inventing a boundary would hide a kit defect.
Report the ambiguity; do not invent a wider scope.

## Do not

- Do not edit the sibling lane "to unblock."
- Do not edit SPEC, INTERFACE, or PLAN from a build seat.
- Do not soft-refuse while still writing forbidden files.
- Do not invent parallel refuse documents.
