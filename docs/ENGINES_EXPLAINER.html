House and guest

Two brains. One window. Same kind of telephone line.

Forge does not “call Grok Studio.” It starts a child process and talks to it in a shared language called ACP, over ordinary stdin / stdout. Chat starts our child. Code starts xAI’s child when the Grok CLI is on the machine.

The 30-second version

Imagine a restaurant kitchen.

The dining room is Forge — the window you see, the buttons, “may I edit this file?”. The kitchen is the model that actually thinks and uses tools.

The waiter does not shout across the kitchen. They pass notes through a tube: one direction is orders (your prompt), the other is plates coming back (thoughts, tool asks, the answer). That tube is stdio. The language on the notes is ACP.

Chat hires our cook (grok-acp). Code hires xAI’s cook when grok.exe is installed (grok agent stdio). Same tube. Different cook. If xAI’s cook is missing, Code honestly uses our cook and labels it Mini-Grok — it does not pretend to be Grok Code.

The tube

What “stdio” actually means

stdio is short for standard input and standard output. Every program has them:

  • stdin — what gets typed into it (the in-tray).
  • stdout — what it prints (the out-tray).
  • stderr — a side channel for logs and complaints, not the official conversation.

When you run a tool in a terminal, you are stdin and stdout. When Forge starts an agent, it hooks those trays to itself. The child never opens a window. It only reads lines and writes lines.

Those lines are not casual chat. They are JSON-RPC: one JSON object per line, with a method name (session/prompt, session/request_permission, …). Forge writes a request on stdin. The agent writes results and notifications on stdout. That is “agent over stdio.”

grok.exe --cwd C:\Dev\your-repo --permission-mode default agent stdio

That command is what Code starts when the Grok CLI is found. agent stdio means: “don’t draw a TUI — sit on the pipe and speak ACP.” It is the headless form of the same product as the Grok terminal UI, not a separate “Studio” app.

There is no Grok Studio in Forge. People sometimes mix that name up with the official Grok CLI / TUI. In this house the guest is that CLI, in stdio mode.
The language on the notes

What ACP is

ACP = Agent Client Protocol. A small, shared contract so a GUI (the client) can drive an agent process (the server) without inventing a private dialect.

Typical moves on the wire:

  • Handshake: who are you, what can you do.
  • Start a session in a folder (Code) or a chat sandbox (Chat).
  • Send a prompt; stream thoughts and text back.
  • Ask permission before a write or a shell command.
  • Advertise extras the agent actually has: skills, MCP servers, child agents, browser work, hooks.

Forge’s StdioAcpClient is the waiter. It spawns the child, frames JSON-RPC, and turns ACP events into the live run you see (You card, Thought, tools, Answered).

Both engines speak ACP over stdio. That is why Chat and Code can share one window, one Review policy, one cancel button. The split is not the protocol. The split is which binary is on the other end of the pipe.

The two children

grok-acp vs grok agent stdio

House child

grok-acp

A Node process Forge ships (packages/grok-acp). Host starts it with Node. It calls xAI itself (subscription pool first, API key backup). It owns a small tool belt: read, list, grep, write, patch, shell, delete, rename — plus Chat extras like PDF extract and pack context.

System prompt and tool policy are ours. Named home, pack pin, honest PDF failure copy — those live here because we wrote them.

UI name in Chat: just Grok. Fallback name in Code: Mini-Grok.

Guest child

grok agent stdio

The official Grok CLI (grok.exe on Windows). Same brain as the Grok TUI. Forge does not reimplement skills, MCP, subagents, or the vendor planner. It shows what that process advertises on the ACP wire.

Spawn is roughly: grok.exe --cwd <repo> --permission-mode default agent stdio. Review → default, Trusted workspace → acceptEdits, Bypass → agent --always-approve stdio.

UI name: Grok Code. Only painted when the host actually spawned this child.

Inside Forge

What happens when you press Send

  1. The window (Voidglass) posts the prompt to the Host on :8788.
  2. The Host decides the child. Chat → grok-acp. Code → probe PATH for grok.exe; if it starts, stamp Grok Code; if not, grok-acp and say Mini-Grok.
  3. ACP over stdio carries the turn. Thoughts, tool calls, and permission asks come back as events. Forge maps Review onto those asks so a write still needs Allow once unless Trusted/Bypass.
  4. Chrome is the house. Plan, File changes, Verify, Git review inspect what happened. Skills / MCP / child agents / browser only appear in Code when the guest advertised them. Chat does not grow a fake catalog.
  5. One live parent run per session. Cancel is “Stopped by you.” Reload must not invent a second brain.

Parked on purpose: chat-on-vendor — putting Chat on grok agent stdio. That would dump email-and-PDF work into a coding agent. It is a product decision for later, not a shortcut.

Honest ledger

Pros, cons, and where each shines

grok-acp (Chat, Code fallback) grok agent stdio (Code)
Who owns the brain Forge. We can ship Chat features (pack, PDF, home) without waiting on CLI releases. xAI. Hard coding jobs match the TUI. We do not maintain a second Grok Build.
Install story Works without Grok CLI. Brother PCs still Chat. Needs grok on PATH. First-run Code must say so, not fake it.
Tools & skills Fixed, small, auditable. Bad at “whatever the TUI grew this week.” Whatever the vendor advertises: skills, MCP, subagents, plan mode. We draw; we do not invent.
Trust Our permission broker and workspace confinement. Known surface. Mapped onto CLI flags. Powerful, and a moving target when the CLI changes.
Failure mode If xAI HTTP fails, Chat fails honestly. No fake “still connected.” If spawn fails, Code falls back to Mini-Grok with a label — never a silent Grok Code badge.
Cost to us We maintain a mini agent forever if we let it grow. We maintain a waiter (ACP client) and chrome. Guest churn is their problem if we stay honest.
Scale

What gets expensive

Process count. Each live Code session is a CLI child. Each Chat session is a grok-acp child. They are not free. One live parent ACP run per session is the cap that keeps cancel/reload honest.

Protocol surface. Scaling by teaching grok-acp to fake vendor skills/MCP/subagents is the expensive future — two brains to keep in sync with xAI. Scaling by showing vendor facts in Forge chrome is cheaper and matches the house/guest bet.

A second guest. ACP is the reason Codex or Claude could sit in the same window later. The house (Review, File changes, Voidglass) stays. Only the spawn line changes. That is the 2.0 story. It only works if we do not bake Grok-only assumptions into grok-acp and then call that “the platform.”

Chat volume. grok-acp is the right scale for everyday text, files, and PDF extract. It is the wrong scale for “run the whole Grok coding product in Chat.” That is why Chat stays off agent stdio for now.

What to do with this

Recommendations

  • Keep the split. Chat = grok-acp. Code = vendor when the CLI is there. Dual engine is the product, not a mess.
  • Do not grow grok-acp into Grok Build #2. New coding powers should come from the guest wire or be marked absent.
  • Do not move Chat onto grok agent stdio as a bugfix. That is a 1.0+ decision with a real UX cost (homes, packs, brother-safe copy).
  • Keep fallback honest. Mini-Grok is allowed. A Grok Code chip without a vendor child is a defect.
  • Invest in the waiter. StdioAcpClient, journals, permission mapping, “Thought is not the answer” — that is the moat. The TUI will keep changing; the house should still inspect what happened.
  • Watch CLI spawn on Windows. PATH, .exe vs .cmd, permission flags as global args before agent. That is operational, not theoretical.
Also worth knowing

Small print that bites

Why both children use ACP if they are so different

So Forge can be a house, not a skin. One client library, one event model, later a second vendor. If Chat spoke HTTP and Code spoke a private TUI dump, we would be gluing two products forever.

Where the API key lives

grok-acp uses Forge’s auth (oauth / key) to talk to xAI. The vendor CLI uses its own login (we strip ambient XAI_API_KEY from the spawn env so the host token is not silently reused). Two auth stories is annoying and correct.

Plan / File changes / Skills in Chat

Those are Code chrome over vendor facts. Chat gating them off is not a missing feature; it is the dual-engine promise. A Plan card on a Chat reload is a leak.

Guest-completeness test

If the Grok TUI can do X, Forge either shows X from the vendor wire or says it is absent. Implementing a fake X inside grok-acp so Code “looks complete” is a defect.
