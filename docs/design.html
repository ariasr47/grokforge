Grok-first Design + Spec v0.2

Grok Code Shell

A local desktop coding agent for Grok first — because Claude and ChatGPT already have strong GUIs/CLIs, and Grok is where a custom shell creates immediate daily value. Architecture still leaves room for Codex and Claude Code later via ACP.

1. Priority decision (updated)

Build Grok integration first. Claude Code and Codex already ship usable desktop/CLI experiences. Grok does not have an equivalent first-class coding GUI for local repos — that gap is the product.
Build now

Grok Code Shell

  • Desktop shell (project, chat, diffs, approvals)
  • Grok ACP agent (tools + xAI)
  • SuperGrok sub-pool OAuth as default
  • API key fallback when pool is exhausted
Build later

Unified multi-agent

  • Codex via official ACP adapter
  • Claude Code via official ACP adapter
  • Agent switcher in the same UI
  • Shared sessions/diffs already exist from Grok work

Implementing Grok first forces the hard shell work (permissions, patches, process host) once. Adding Codex/Claude later is mostly registry entries + onboarding copy.

2. Product definition (v1)

One-liner: Local project agent powered by Grok — subscription pool by default, API as backup.

UserJob to be done
You (solo)Open a repo, ask Grok to explore/fix/test, review diffs, keep using SuperGrok quota
Future youSame window, optionally switch to Codex or Claude without rebuilding the app

In scope (v1)

  • Open a local folder as workspace
  • Chat thread with streaming replies
  • Tools: read file, list/search, apply patch, run shell command
  • Permission prompts before write/shell
  • Diff view for proposed edits
  • Grok auth: OAuth sub-pool + API key

Out of scope (v1)

  • Codex / Claude wiring (architecture only)
  • Full IDE (LSP, debugger, git GUI)
  • Multi-user or sharing one sub across people
  • Browser scraping of grok.com

3. Architecture (Grok-first)

The shell speaks ACP even when only Grok exists, so the host is not rewritten for multi-agent later.

Implementation order: ship API-key mode first so the agent loop works immediately; then add OAuth and make sub-pool the default. Dual-mode stays in the design either way.

5. Implementation spec

5.1 Repo layout

grok-code-shell/
├── apps/
│   └── shell/                 # Tauri (preferred) or Electron + React UI
├── packages/
│   ├── acp-client/            # JSON-RPC stdio client, session types
│   └── grok-acp/              # ACP agent process for Grok
├── docs/
│   └── SPEC.md                # this living spec
└── README.md

5.2 Package: acp-client

  • Spawn child with cwd = workspaceRoot
  • Methods: initialize, session/new, session/prompt, cancel/dispose
  • Normalize notifications into UI events: text_delta, tool_request, permission_request, file_edit, error, done
  • One subprocess per active thread (v1 simplicity)

5.3 Package: grok-acp

  • stdio ACP server compatible with the host client
  • Model calls to xAI (streaming)
  • Auth provider interface: SubPoolAuth | ApiKeyAuth
  • Tools (workspace-scoped):
    • read_file(path)
    • list_dir(path) / grep(pattern, glob?)
    • apply_patch(path, diff) or write with preview
    • run_shell(command) — always permission-gated
  • Path allowlist: cannot escape workspace root
  • On pool/rate limit: structured error the UI can map to “Switch to API key”

5.4 App: shell

  • Project: open folder, show root name, recent projects
  • Chat: streaming markdown transcript
  • Permissions: modal for shell/write; remember “allow for session” optional
  • Diffs: side-by-side or unified; Accept / Reject
  • Settings: Sign in with Grok · paste API key · clear auth · model id
  • Status chip: Grok · sub-pool | Grok · API | Signed out

5.5 Config sketch

{
  "workspace": "/path/to/repo",
  "agent": {
    "id": "grok",
    "command": "node",
    "args": ["./packages/grok-acp/dist/index.js"],
    "model": "grok-4"
  },
  "auth": {
    "mode": "sub_pool",
    "apiKeyRef": "keychain:xai_api_key"
  },
  "permissions": {
    "autoApproveRead": true,
    "autoApproveWrite": false,
    "autoApproveShell": false
  }
}

5.6 Security rules (non-negotiable)

  • All tool paths resolved under workspace; reject .. escapes
  • Shell runs with explicit user approval (or session policy)
  • Secrets in OS keychain, not plaintext config in git
  • No embedding of other users’ credentials; single-user app

6. Milestones (Grok-first)

M0

Skeleton

Shell opens, select folder, empty chat UI, settings page stub. No model calls.

M1

API-key Grok loop

grok-acp + host: prompt → stream text only (no tools). Proves transport + xAI connectivity.

M2

Read tools

read_file / grep / list_dir with auto-approve reads. Agent can answer about the repo.

M3

Write + shell + diffs

Patches and commands behind permissions; diff pane Accept/Reject. Daily-driver usable.

M4

Sub-pool OAuth

Sign in with Grok; default mode sub-pool; API key remains fallback; status chip accurate.

M5

Hardening

Cancel run, restart agent, error copy for limits, basic logging, README first-run.

7. Later: multi-agent (unchanged north star)

flowchart LR UI[Same shell] --> Host[ACP host] Host --> G[Grok] Host --> X[Codex] Host --> C[Claude Code]

After M5, add agent registry entries for Codex and Claude adapters. No change to transcript/diff/permission components — only spawn target + auth onboarding.

8. Acceptance criteria (v1 done)

  • Open a real repo and ask Grok what the entrypoint is (uses read tools)
  • Ask for a small bugfix; see a diff; accept; file on disk matches
  • Shell command requires approval and shows output in the thread
  • API-key mode works end-to-end
  • Sub-pool sign-in works and status shows subscription mode
  • On pool/limit error, UI offers switch to API key without crashing
  • Agent cannot read/write outside workspace root
